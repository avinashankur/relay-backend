# 003-ADR: Use RS256 for JWT Access Tokens

**Date:** -
**Status:** Accepted
**Deciders:** Engineering Team
**Tags:** auth, security, cryptography, jwt

---

## Context

Relay issues short-lived JWT access tokens for API authorization. We need to establish the cryptographic algorithm used to sign these tokens. The two most common algorithms for JWTs are HS256 (symmetric HMAC) and RS256 (asymmetric RSA).

Relay is designed as a central identity provider. As the platform scales, it is highly likely that other internal microservices or external third-party applications (acting as resource servers) will need to verify the validity of these access tokens independently, without making a network call back to Relay on every request.

## Decision

We will use **RS256 (RSA Signature with SHA-256)** for signing all JWT access tokens.

Relay will securely store and use an RSA private key to sign the tokens when they are issued. Relay will also expose the corresponding RSA public key (eventually via a standard JWKS endpoint) so that any consuming service or client can cryptographically verify the token's authenticity.

## Alternatives Considered

### Option A: HS256 (HMAC with SHA-256)

- **Description:** Using a single, symmetric secret string to both sign and verify the tokens.
- **Pros:** Computationally faster to generate and verify. Extremely simple to implement and manage (just one string in the environment variables).
- **Cons:** The secret key must be shared with any service that needs to verify the token. If _any_ of those resource servers are compromised, the shared secret is exposed, allowing an attacker to mint valid, arbitrary access tokens for the entire system.
- **Why we didn't choose it:** It tightly couples security across the entire infrastructure. It breaks the zero-trust model required for an enterprise identity provider, as it forces the identity provider to trust every downstream consumer with its signing secret.

## Consequences

### Positive

- **Decentralized Verification:** Downstream resource servers only need the public key to verify tokens. They cannot forge new tokens.
- **Blast Radius Containment:** If a downstream service is compromised, the attacker only gains access to the public key (which is public by design). The ability to mint tokens remains safely isolated within Relay.
- **Industry Standard:** This aligns with OIDC (OpenID Connect) standards and enterprise identity patterns, ensuring interoperability with standard libraries and API gateways.

### Negative

- **Performance Overhead:** RS256 is computationally heavier than HS256 for both signing and verifying, though this is negligible at our current scale and easily offset by the stateless nature of the tokens.
- **Operational Complexity:** Managing RSA key pairs (generation, secure storage in AWS Secrets Manager, and implementing 90-day key rotation schedules) introduces significantly more infrastructure complexity than managing a single symmetric secret.

## Follow-up Actions

- [ ] Implement key rotation logic to support multiple active keys (using the `kid` header in the JWT) during the 7-day grace period of a key rotation event.
- [ ] Ensure the RSA private key is never committed or passed via `.env` files in production, but dynamically loaded from a secure secrets manager.
